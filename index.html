Synthetic Cohort Generator

Selected scenario

Create a reproducible, non-identifiable demonstration cohort representing patients diagnosed from childhood through age 39. Each generated record links demographic characteristics, cancer type and risk, treatment exposures, eligibility for care processes, completion of recommended care, follow-up, a simulated two-year outcome, and a deliberately imperfect prediction score.

Known ground truthEach scenario injects a documented mechanism—such as differential missingness, lower completion of indicated care, or subgroup miscalibration—so the downstream auditors can be tested against a known expected signal.
Reproducible experimentsThe same scenario, cohort size, and seed always produce the same records. Change only one setting at a time to compare how an audit responds while other assumptions remain stable.
Privacy-first demonstrationEvery patient is simulated in the browser. No real individual, CCDI participant, protected health information, or controlled-access record is used or transmitted.
All computation remains in this browser tab.
How to use this module
  1. Select a scenario that represents the data, care, or model behavior to evaluate.
  2. Choose a sample size and seed, then generate the cohort.
  3. Use Sections 02–04 to determine whether the known signal is detected across populations.
  4. Download synthetic CSV/JSON for reproducible testing, teaching, or integration work. Generated values are engineering demonstrations, not epidemiologic estimates.

What does the risk threshold mean?

The active score estimates a synthetic two-year adverse-outcome probability from a fixed baseline exactly 180 days after diagnosis. At 20%, for example, scores at or above 0.20 are classified as model-positive. The cutoff is an exploratory software setting—not a validated cancer-treatment threshold. Changing it alters who is flagged and therefore sensitivity, false-negative rates, false-positive rates, and measured group differences.

Outcome follow-up begins after the day-180 landmark. Observed events receive an outcome date; records lost before an event or the 24-month horizon are censored and excluded from binary performance metrics rather than counted as event-free. Clinical thresholds must be tied to a named model, outcome, time horizon, intended action, and supporting publication or guideline. No universal threshold applies across childhood and AYA cancers. See the synthetic-data specification, evidence-to-variable matrix, and Kartoun et al. fairness framework.

2. Export reviewable artifacts

What the downloadable files contain

Demonstration node bundle

A JSON package that separates synthetic study, participant, diagnosis, treatment, and survival nodes. Identifiers preserve relationships across nodes so mapping logic can be inspected and tested without exposing real patients.

Aggregate audit report

A disclosure-conscious JSON report containing cohort configuration, readiness results, care-process rates, model performance, fairness measures, and threshold settings. It contains aggregate findings and metadata—not participant-level rows.

Canonical schema

The JSON Schema defines field names, data types, required columns, and accepted categories. It can support automated validation in a data-submission or analysis pipeline.

3. What CCDI adaptation could achieve

A reusable quality and equity checkpoint before downstream analysis

Earlier data-quality detection

Identify missingness, sparse subgroups, invalid codes, and incomplete follow-up before a dataset is reused or a model is fitted.

Comparable care-process measures

Apply explicit eligibility and upstream denominators so testing, treatment, adherence, survivorship, and fertility pathways are interpreted consistently.

Model-governance evidence

Package subgroup discrimination, calibration, error rates, threshold behavior, and confidence intervals in a reproducible aggregate report.

Versioned interoperability work

Maintain traceable mappings from source fields to controlled terminology, CCDI structures, and—where applicable—mCODE or pediatric FHIR profiles.

Privacy-conscious collaboration

Use synthetic examples and aggregate outputs for review while keeping controlled participant data inside authorized environments.

Repeatable acceptance testing

Run known-ground-truth scenarios and automated checks whenever a schema, adapter, dataset version, or analytical model changes.

4. Proposed milestone adaptation path

Work required for a selected CCDI target

  1. Select the destination.Confirm the CCDI resource, submission template, data-model version, and intended analytical use with NCI/CCDI.
  2. Profile and map.Create a field-level crosswalk covering terminology, identifiers, provenance, units, missing-value semantics, and permitted transformations.
  3. Represent relationships.Add required multi-table and longitudinal links among participants, diagnoses, treatments, specimens, outcomes, and follow-up events.
  4. Validate and document.Package validation rules, example manifests, transformation logs, data dictionaries, version history, tests, and disclosure controls.
  5. Evaluate safely.Test the adapter and audits with approved data in an authorized environment; compare expected and observed findings with CCDI collaborators.
  6. Prepare for reuse.Deliver documented code, synthetic fixtures, schemas, model cards, aggregate reports, and deployment instructions for iterative CCDI review.
Integration status: The current DBbun schema and node bundle are demonstrations informed by public CCDI descriptions. They are not official CCDI templates and have not yet been reviewed, endorsed, or integrated by NCI/CCDI. No controlled-access data should be uploaded to the public demonstration.
